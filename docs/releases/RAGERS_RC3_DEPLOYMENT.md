# Ragers RC3 — deployment and rollback record

**Classification:** Internal. **Nothing in this document is hosted evidence.** RC2 ended with four
release dimensions `BLOCKED` on things no amount of code produces, and this records what Batch 1 did
about the two that code can move towards — plus, precisely, what is still missing and who has to
supply it.

|---|---|
| **Release candidate** | RC3, Batch 1 |
| **Baseline** | Phases 1–100 merged (`6f48058`). E1–E12. No Engine 13 |
| **Branch** | `feat/ragers-rc3-deployment` |
| **Scope** | Deployment target, hosted Postgres, real authentication, object storage, hosted readiness, rollback preparation |
| **Not in scope** | Phase 101+ product features. No certified 1–100 behaviour is reopened except where deployment exposed a real defect |
| **Authoritative evidence** | `docs/EVIDENCE.md`, regenerated by `npm run certify` |

## The distinction this document exists to hold

`DEPLOYMENT_READY` and `ROLLBACK_READY` are **still `BLOCKED`**, and everything below is written so
that cannot be misread. Batch 1 certified the half that can be certified without a target: that the
schema, the credential and the composition root behave against a real Postgres, and that the failure
modes a deployment actually hits are refusals rather than silent wrong answers.

A gate that passed on this machine and were reported as `DEPLOYMENT_READY` would be certifying a
laptop. **There is no deployment. Nothing here claims otherwise.**

## 1. Target

Inspected before choosing: the repository already assumes Next.js 15 with a dependency-free engine
core, `pg` as the only database client, a `supabase/migrations` directory applied by the repo's own
runner, and a standalone worker entry point (`scripts/worker.ts`) that already shares its
composition with the web tier.

| Concern | Target | Why |
|---|---|---|
| **Web tier** | Vercel | Named by the owner. The app is a standard Next.js 15 App Router build with no custom server, so nothing in the repo resists it |
| **Worker** | A long-running container (Railway, Fly, or a small VM) | **Not Vercel.** The drain loop is a process that must stay alive between requests, hold leases, and recover them after a crash. A serverless function cannot hold a lease it might be frozen in the middle of, and a cron-triggered invocation would make lease recovery depend on the cron's cadence rather than on the lease's TTL |
| **Database** | Hosted Postgres | **Provider not chosen — see the open questions.** Requires `pgcrypto`-free plain Postgres 16, RLS, and a connection pooler the `pg` client can speak to |
| **Object storage** | **Not chosen — see the open questions** | The port exists and its fail-closed behaviour is certified against a fake |
| **Second application runtime** | None | Explicitly not introduced. The engine is authoritative and PR #6 is closed; `docs/architecture/CONVERGENCE_1_50.md` records that disposition |

### Topology

```
  Vercel (web)                 container (worker)
  ├─ RAGERS_DISABLE_WORKER=1   ├─ npm run worker
  ├─ /api/*  reads + commands  ├─ drains the outbox
  ├─ /api/health               ├─ recovers expired leases
  └─ /api/readiness            └─ runs scheduled sweeps
            │                            │
            └────────── one Postgres ────┘
```

**One worker process, and the web tier must not also drain.** Both entry points go through
`configuredDb()` so they cannot disagree about which database they hold — the defect PR #5 found —
but two drain loops racing the same outbox is a different problem: the leases make it *correct* and
make it pointless, because each event is delivered once and the second process spends its time losing
races. `RAGERS_DISABLE_WORKER=1` on the web tier is not an optimisation; it is which process owns the
loop.

## 2. Environment

| Variable | Where | Required | What it does |
|---|---|---|---|
| `DATABASE_URL` | web + worker | **Yes, in any deployment** | The Postgres the engine uses. Absent on a hosted process, `configuredDb()` **throws at construction** rather than falling back to memory |
| `RAGERS_DEPLOYMENT` | web + worker | Recommended | `local` declares a local process. Anything else, or a Vercel platform signal, means hosted |
| `RAGERS_DISABLE_WORKER` | web | **Yes**, set to `1` | Stops the web tier starting its own drain loop |
| `RAGERS_TEST_SEED` | nowhere | **Must be absent** | Enables the fixture route *and* passwordless sign-in. Both are test-only and both are gated on this one flag |
| `RAGERS_OBJECT_STORAGE_READY` | certification only | No | Flips `OPERATIONS_READY` when live delete/retention proof exists |
| `RAGERS_BENCHMARK_DATA_READY` | certification only | No | Flips `DATA_READY` when real volume exists |
| `RAGERS_LIVE_PROVIDERS_READY` | certification only | No | Flips `PROVIDER_READY` when provider credentials exist |
| `RAGERS_SIGNIN_CREDENTIALS_READY` | certification only | No | Flips `SECURITY_READY` when hosted sign-in proof exists |

Not read anywhere, deliberately: **`NODE_ENV`**. `next build` sets it to `production` on a laptop, so
a check on it would call a local build hosted — and, far worse, would call a real deployment that
forgot to set it *local*, failing open in exactly the case that matters.

**`RAGERS_TEST_DATABASE_URL` is not read by the application tier.** It is the certification harness's
variable, exported whenever a live database is available, and honouring it in `configuredDb()` made
the browser gate exercise a different backend depending on the environment — 23 of 30 browser tests
failed before anyone chose it.

### Secrets

`DATABASE_URL` is a credential. Nothing logs it, `/api/readiness` reports only that a database is
*configured*, and `configuredDatabaseUrl()` exists to answer presence rather than value. The
readiness response is swept by a test for connection strings, passwords, tokens and keys, because
that endpoint is usually the most reachable thing a deployment has: no auth, no rate limit, polled
every few seconds.

## 3. Migration order

```bash
cd engine
npm ci
npm run migrate     # applies 0001 … 0020 in order, recording a checksum per file
npm run build
```

**Migrations run before the new code is serving, and they are additive.** Every migration in this
repository adds; none drops a column or narrows a type. That is the property the rollback strategy
depends on, so it is a rule rather than an observation:

> A migration must be safe to have applied while the *previous* release is still running.

The runner refuses to proceed against a drifted schema. Editing an applied file produces
`schema drift: <file> was applied with checksum <a> but is now <b>` and the runner stops — drilled in
RC2 by tampering with a recorded checksum.

## 4. Health and readiness

| Path | Answers | Caller |
|---|---|---|
| `/api/health` | Are my dependencies up? | A person, or an alerting system |
| `/api/readiness` | May a balancer send me requests? | The platform's health check |

They are not the same question, and conflating them routes traffic at an instance that is healthy and
unfit. Readiness returns **503** when not ready, so a balancer's default behaviour is correct with no
configuration.

Seven checks. The four added in RC3 share one shape: **a fact no probe could discover by asking.**

| Check | Fails when | Gates rotation |
|---|---|---|
| `store` | The store did not answer | Yes |
| `worker` | No worker registered, so projections would not advance | Yes |
| `not_forced_degraded` | An operator declared degraded mode | Yes |
| `persistent_store` | Hosted and in-memory | Yes, hosted only |
| `sign_in` | The credential check is disabled, or the credential store is unreachable | Yes |
| `object_storage` | Hosted and the store is not durable | Yes, hosted only |
| `providers` | Never — it reports | No |

`sign_in` is the one worth naming: it reports **the state RC2 shipped.** Running, healthy, every read
correct, and unusable by anybody not already holding a session. No probe said so because no probe
asked.

`providers` reports and does not gate on purpose. A deterministic fallback model provider is a
degraded product rather than an unfit instance — agents escalate to a person instead of proposing,
which is what the fallback exists to produce — and taking a deployment out of rotation over it would
be the wrong trade.

## 5. Authentication

A credential exists as of this batch. `identity.authenticate` requires a password; migration 0020 adds
`actor_credentials`; `src/domain/credential.ts` holds the mechanism.

**Password rather than magic link, and the reason is a missing provider rather than a preference.** A
verified magic link or an OTP is the better mechanism and needs a transport — something that delivers
a token to an address the person controls. No email or SMS provider exists in this repository, and a
one-time token nothing can deliver is a table rather than an authentication mechanism.

The consequence is stated rather than glossed: **a password is replayable if it is captured.** That is
why the session cookie gains `Secure` on every hosted deployment, why HTTPS is not optional, and why
this is written here instead of in a commit message nobody re-reads.

| Property | How |
|---|---|
| No email-only session issuance | The credential check is in the engine, not the route: a caller reaching the bus directly still faces it |
| Secure hashing | scrypt (`node:crypto`, so no new dependency), memory-hard, 32 MB per verification, parameters stored **per row** so raising the cost is a rotation rather than a migration |
| No account-existence oracle | Six internal outcomes return one code and one message — **and** the no-account path spends a decoy derivation, because otherwise the clock answers what the message refuses to |
| Session expiry | 30 days, and a session is revocable |
| Session rotation | Signing in revokes every other live session for that actor. The one recovery action a person can take unaided |
| Revocation | `identity.revokeSession`, audited. Revocation is not suspension: the credential still works afterwards |
| Rate limiting | Per credential: five consecutive failures earn a doubling window to a 15-minute cap, refused with the *same* refusal so the window is not an oracle either |
| Nobody sets anybody else's password | `setPassword` takes **no target parameter at all**. `resolveResource` returns the caller, so there is no field through which an admin could name another account |

### What authentication still lacks

- **No password reset.** There is no column a password could be read from, so recovery has to be a
  reset, and a reset needs the same transport a magic link needs. **Somebody who forgets their
  password today cannot recover their account.** This is the single largest product gap in the batch.
- **No second factor.**
- **Per-caller rate limiting does not exist**, and a per-actor window cannot express "this caller".
  The credential backoff throttles guessing at one known account and **also lets somebody who knows
  an email address make that account wait** — a denial of service against one person. The alternative
  is no limit at all, which is worse. The proper answer is per-caller throttling at the edge, which
  is configuration rather than code.

`SECURITY_READY` therefore stays **`READY_WITH_CONDITIONS`**. It does not become `READY` on local
proof, and it should not become `READY` until a reset path exists and hosted sign-in has been
exercised.

## 6. Object storage

The port and its fail-closed behaviour are certified against a fake. `ObjectStore` now states its own
`name` and `durable`, because durability is the one fact no call can reveal: the in-process store
answers `put`, `exists` and `remove` successfully, and the difference appears on restart, when
somebody's recording is gone and the row describing it is still there.

Retention already states its ceilings, enforces its holds, decides expiry and writes its ledger.
Deleting remote bytes reports `object_storage_blocked`.

**No provider is wired, because choosing one is a deployment decision rather than a coding one** —
see the open questions. `OPERATIONS_READY` stays `READY_WITH_CONDITIONS` and must not move until a
live delete and a live retention sweep have both been observed against a real bucket.

Requirements for whichever provider is chosen, so the choice can be checked against them:

- Private by default. **No raw public object URL is ever produced** — `media_assets.original_key`,
  `transcripts.raw_text` and `evidence.original_key` must stay unreadable on every path for every
  role, admin included.
- Signed, short-lived URLs for upload and download.
- Deletion that returns a result the retention ledger can record, so "we deleted it" is a fact rather
  than an assumption.
- A governed refusal when the provider is unavailable, never a local filesystem fallback: bytes
  written to a container's disk are lost on the next deploy, and *silently*.

## 7. Rollback

### Last known good

|---|---|

| **This branch adds** | 0020 (`actor_credentials`) |

### The compatibility rule

> **A release may be rolled back by deploying the previous image. A migration may not be rolled back
> to roll back a release.**

That works only because migrations are additive, which makes the rule a constraint on every future
migration rather than a description of the current ones:

- **Adding** a table, a column, an index or a constraint that the previous release ignores → the
  previous release keeps working, so the rollback is code-only.
- **Dropping or narrowing** anything → the previous release may still be writing to it, so the
  rollback is **not** code-only and the migration needs an expand/contract pair across two releases.

`0020` is purely additive: nothing before RC3 reads `actor_credentials`. Rolling back to `6f48058`
with `0020` applied leaves an unused table and a working product — with credential-free sign-in
refused, because RC2 already refused it.

### App rollback versus irreversible migration

| Change | Reversible by redeploying? | Why |
|---|---|---|
| Any code change | Yes | The schema is a superset of what the old code needs |
| An additive migration | Yes, code-only | The old release does not know the new objects exist |
| A `drop`, a type narrowing, a `not null` on an existing column | **No** | Requires a restore, which loses everything written since the backup |
| Data written by the new release | **No** | A rollback does not un-write rows. A credential set under RC3 survives a rollback to RC2, where nothing reads it |

**No rollback in this repository assumes it may destroy data.** The one migration drill that has run
(RC2) proves the runner *refuses* a drifted schema; it does not prove a rollback, because a rollback
needs somewhere to roll back from.

### Checklist

Before any deploy:

1. Record the current SHA and the highest applied migration. Both, because a SHA alone does not say
   what the schema is.
2. Confirm the new migrations are additive. If any is not, stop: it needs an expand/contract pair.
3. Take a backup and **verify the restore** — `tests/live/backup.restore.test.ts` drills the
   mechanism; a hosted backup nobody has restored is a hope.
4. Apply migrations. Confirm the runner reports no drift.
5. Deploy the worker before the web tier, so no event waits for a drain loop that does not exist yet.
6. Watch `/api/readiness` on the web tier until it returns 200.

To roll back:

1. Redeploy the previous image on **both** tiers. Do not touch the schema.
2. Confirm `/api/readiness` returns 200 and the outbox is draining.
3. Leave the newer migrations applied. Reverting them is a separate, considered decision and is
   almost always wrong.
4. Record what was rolled back and why, in this file.

`ROLLBACK_READY` stays **`BLOCKED`**, and the reason is not a missing procedure — it is that a drill
needs a deployed environment. **No rollback proof will be fabricated.**

## 9. Open questions for the owner

Three decisions that are infrastructure rather than code, and each commits money, a vendor, or both.
Batch 1 stops here rather than choosing.

1. **Hosted Postgres provider.** Supabase is implied by `supabase/migrations` and is not required by
   anything — the engine speaks plain Postgres 16 through `pg`. Neon, Supabase and RDS all work.
   Needed: which one, and whether the pooler is transaction-mode (which the transactional outbox is
   fine with) or session-mode.
2. **Object storage provider.** Supabase Storage is the smallest step if the database is Supabase —
   bearer token, plain REST, no new dependency. S3 or R2 needs SigV4, which is writable against
   `node:crypto` but is real work. Cloudflare R2 is cheapest at volume. **The requirements in §6 are
   what any of them must satisfy.**
3. **Worker host.** Railway, Fly, or a VM. Any of them works; the constraint is that it is a process
   which stays alive, not a function.

A fourth, which is product rather than infrastructure and blocks `SECURITY_READY` more than any of
the above: **an email provider**, without which there is no password reset and no magic link.
