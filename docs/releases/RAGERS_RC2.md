## Readiness, by dimension

Eight dimensions, read independently by `src/certification/release.ts`. **No dimension can be set
by hand** — each is derived from the gates and from what the environment provides, because a
dimension somebody could write would be written `READY`.

`BLOCKED` and `NOT_READY` are different values. `NOT_READY` means *we looked and it is not good
enough*; `BLOCKED` means *we could not look*, because the evidence needs something this environment
does not have. Collapsing them would make a deployment nobody can attempt read as a deployment that
failed, and the fix for those two is not the same.

| Dimension | Value | Waiting on |
|---|---|---|
| `CODE_READY` | **READY** | — (28 gates) |
| `SECURITY_READY` | **READY** | — (15 gates) |
| `BROWSER_READY` | **READY** | — (3 gates, 41 browser tests) |
| `OPERATIONS_READY` | **READY_WITH_CONDITIONS** | Object storage. Retention states its ceilings, enforces its holds, decides expiry and writes its ledger; deleting remote bytes reports `object_storage_blocked` until a bucket exists |
| `DATA_READY` | **BLOCKED** | Twenty distinct contributors per comparison set. A gate that passed against seeded volume would be certifying the seed |
| `PROVIDER_READY` | **BLOCKED** | Credentials for a transcription/PII provider and a model provider. An interface is not a certified provider |
| `DEPLOYMENT_READY` | **BLOCKED** | No deployment target is configured |
| `ROLLBACK_READY` | **BLOCKED** | Requires a deployed environment to roll back |

## Decisions

| Decision | Verdict | Why |
|---|---|---|
| **Controlled validation** | **GO** | `CODE_READY`, `SECURITY_READY`, `BROWSER_READY` and `OPERATIONS_READY` are all satisfied. These four are about this codebase; requiring the other four would mean nothing could be validated before it was deployed, which is backwards |
| **Production pilot** | **NO_GO** | `DATA_READY`, `PROVIDER_READY`, `DEPLOYMENT_READY` and `ROLLBACK_READY` are all `BLOCKED`. A pilot puts real people's accounts of real things into a system, and there is no subset of the eight that makes one responsible |

`decide()` takes no override parameter. A function with a `force` argument would be called with
`force` by somebody under pressure, and the ledger would then say GO about a release nobody had
evidence for.

## What Phases 91–100 added

The band's question: **when this system does something, can a human see why, stop it, and prove what
happened?** Almost every mechanism already existed; what did not exist was the contract.

- **P91 agent authority.** Five fields added to every declaration: target engines (distinct from
  what it reads), a forbidden-command allowlist, the required platform role, an evidence floor, and
  a degraded behaviour. Default deny. Nothing may target E12.
- **P92 explainability.** One shape over the eight existing `explain*` functions, including a
  **withholding reason** — because the failure mode is silence, not a lie.
- **P93 provenance.** The chain `proposal → reviewer → decision → authority → command → target →
  effect or refusal`, read from four tables that already held every link and were never joined.
  Refusals stay in it.
- **P94 human override.** Six governed server-side controls over `operator_controls`
  (migration 0019). This did not exist in any form.
- **P95 containment.** Seven failure classes, each with its blast radius *and* what still works.
- **P96 replay.** `replay != re-decide`, with four classes and a source sweep proving no consumer
  generates an idempotency key.
- **P97 observability.** The nine operator questions, each answered from a durable record. Added
  `/api/readiness` — distinct from `/api/health`, because an instance whose projections nothing
  advances is healthy and must not be in rotation.
- **P98 privacy.** Twelve enumerated rules against a live schema.
- **P99 release readiness.** This document's contract.
- **P100** the whole circle, Rage and Rave, plus eight named scenarios.

## Defects found in this band

1. **`isBlockedBetween` said "Consulted on every read path" and was consulted on one** —
   notifications. Blocked authors' accounts were served into the blocker's personalized feed and
   search results. Found in Phase 86, fixed there.
2. **`executePlan` never compared its steps to the ones the approval covered.** Scope escalation:
   a step the reviewer never saw, run under their name. Fixed in Phase 89.
3. **`requiredAuthority` accepted `'organization'`, which is not a role** — a membership and a rank
   merged into one enum, in the very field meant to keep agent authority and actor authority apart.
   The `organization_response` agent was unactionable the moment the check landed.
4. **The release contract leaked an external blocker into `CODE_READY`.** Unscoped `deployment` and
   `rollback` gates defaulted to engine scope, so two blocked external gates turned `CODE_READY`
   from `READY` into `READY_WITH_CONDITIONS` — exactly the failure Phase 99 exists to prevent, in
   the function written to prevent it. Gate ownership is now single and explicit.
5. **`actionDescribed` measured response kinds that do not exist**, so no organization could ever
   have read as `good`. Found in Phase 84.
6. A **privacy test of mine demanded a hole in moderation** — it asserted that *no* role could read
   a trust assessment, including operators. The policy is `is_staff()` and it is right: trust is a
   moderation input. The rule is that it never reaches a member or a stranger, including the person
   it is about. The test was corrected, not the code.

## Release gap sweep

Inspected for release-critical contradictions only. **Nothing found** in: dead event subscriptions
(39 subscribed, all produced), orphan commands (57 registered, all dispatched), migration drift (75
adapter relations, all created), unsafe `security definer` functions (both pin `search_path`),
unaudited decisions (the Phase 68 sweep passes), critical routes (`/api/health` and
`/api/readiness` both present; the `RAGERS_TEST_SEED` fixture route stays gated), and hidden
provider dependencies (the deterministic assistance provider reports `live: false` and the webhook
transport records `pending` rather than claiming a send).

Two sweeps of my own were wrong before they were right, and both are worth recording because the
wrong versions looked authoritative: the first treated `aggregateType` values as event names, and
the second stripped `events:` arrays — which are *also* where events are emitted — so it reported
52 dead subscriptions where there are none.

## Risks

- **The deterministic assistance fallback answers below most agents' confidence floors**, so with no
  model configured agents escalate rather than propose. That is correct behaviour and it means the
  proposing path is exercised only against a stubbed confidence. Live model behaviour is unproven.
- **The PII detector has a known person-name false positive** (two capitalised words read as a
  name), which routes experiences naming an organization to review. Recorded in
  `docs/architecture/ENGINE_GAPS.md`; it fails closed and costs a moderator's time.
- **Guest rate limiting by address does not exist.** A per-actor window cannot express "this
  caller", and throttling the shared `guest` identity would throttle everybody. Belongs at the API
  layer, named rather than faked.
- **A client cannot read its own reaction state.** Phase 69 withheld `reactions.actor_id` from
  client roles, which closed a real leak and left a real need unmet. The answer is a `my_reactions`
  view scoped by `current_actor_id()`, deliberately not built because nothing reads it yet.
- **No load or soak evidence.** Every concurrency proof is a small-N race against a real database.
